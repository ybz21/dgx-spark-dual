# 双 Spark 部署实操注意事项（46/141 集群一天混沌测试的全部教训）

按发生顺序排列的六个坑与对策。配套自动化在 `../scripts/roce-autoconf/`（光口/GID 自适应）
与 `../scripts/watchdog/`（自愈看门狗 + 开机清缓存），装上后以下问题全部无人值守自愈。

## 1. 手工配的光纤 IP 会被 NetworkManager 回收
`ip addr add` 的地址 NM 会刷掉（不止重启丢，运行中也可能丢）。必须写成 NM 静态连接
（roce-autoconf 自动处理）。

## 2. NCCL_IB_GID_INDEX 不能照抄，且会漂移
GID index 是网卡 GID 表行号，取决于口上地址的数量与顺序：机器之间不同（我们一台 5 一台 6），
重启/网络事件后还会漂。选错的症状：`ibv_modify_qp failed with 22/61`、对端 GID 显示 `::`，
无限崩溃循环。必须每次开机实测（roce-autoconf），且容器 env 过期后要重建容器（watchdog）。
**GID 漂移的元凶**是 NM 自动生成的"有线连接"配置在光口上反复 DHCP：部署时把光口上除
静态连接外的 NM 配置全部 `autoconnect no`。

## 3. 旧 kernel 缓存 + cudagraph 捕获 = 启动崩环
带上次运行的 vllm-cache 重启时，autotune 缓存命中会把某些 kernel 的首次加载推迟进
cudagraph 捕获窗口 → `Triton Error [CUDA]: operation not permitted` 无限循环。
对策：开机清一次缓存（ds4-clear-kernel-cache.service）。代价 = 每次整机重启多几分钟
冷编译，换启动确定性。

## 4. TP=2 的两个 rank 只在进程启动时集合
集合窗口约 10 分钟（`Timed out after 601 seconds`）。任何一边换了新进程，另一边必须
也重启一次才能会合；双机同时开机时各自的"捅对端"时点错位会白烧整个周期。
对策：**窗口纪元对齐**（watchdog）——head 每换新实例且未组网（日志无 `Init COMPLETE`）
就立刻 restart worker，两端必然同窗。

## 5. 镜像里烧死了 GLOO/TP_SOCKET_IFNAME=管理口
gloo/TP 控制面通道默认指向管理网口。worker 不插管理网线（真实交付常态）时 gloo 找不到
地址直接崩：`gloo ... Unable to find address for: enP7s7`。对策：compose 里把
`GLOO_SOCKET_IFNAME`/`TP_SOCKET_IFNAME` 跟随 `NCCL_SOCKET_IFNAME`（光纤口）。

## 6. 健康探测必须打穿数据面
`/v1/models` 只测 API 进程：光口挪走后它照样 200，而推理已死（假活）。
探针要用 1-token 真补全（watchdog 已内置）。

## 时间预期（GB10 x2 实测）
- 整机重启（单台/双台）→ 恢复 10–15 分钟（含开机清缓存后的冷编译）
- 光纤换口/拔插 → 8–15 分钟
- 运行期容器崩溃 → 分钟级（保留缓存快路径）
- **卡死兜底阈值 15 分钟不要调小**：冷启本身就要 12–15 分钟，调小会把正常启动误杀成无限重启。
